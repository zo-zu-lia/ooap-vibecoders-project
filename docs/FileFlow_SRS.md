## 1. Вступ

### 1.1. Призначення документа

Документ визначає вимоги до FileFlow та проєктну архітектуру, на підставі яких можна реалізувати і протестувати MVP. Аудиторія — розробники, тестувальники, адміністратори компанії та замовник. Вимоги позначено ідентифікаторами `FR-*` і `NFR-*` та доповнено перевірними критеріями приймання.

### 1.2. Призначення продукту

**FileFlow** — внутрішня вебсистема для безпечного зберігання, організації та обміну робочими файлами між працівниками однієї компанії. Замість пересилання документів електронною поштою користувач отримує спільні робочі простори, папки, історію версій, контрольований доступ і журнал операцій.

Основна відмінність від публічного Dropbox — **відсутність багатоклієнтської SaaS-моделі**: існує одна компанія, її корпоративний каталог працівників та її власні правила доступу. Водночас у системі можуть бути декілька робочих просторів для відділів або проєктних команд.

### 1.3. Межі MVP

**Входить до MVP:** корпоративний вхід (SSO), робочі простори та папки, multipart upload, перевірка файлів, незмінні версії та відновлення версій, завантаження, права доступу, внутрішні тимчасові посилання, пошук за назвою, кошик, retention, legal hold, адміністративні політики й аудит.

**Не входить до MVP:** мобільний застосунок, повноцінний desktop-клієнт із офлайн-синхронізацією, редагування документів у реальному часі, обмін з користувачами поза компанією, повнотекстовий пошук у вмісті документів, DLP-аналітика, багаторегіональна реплікація та власний механізм корпоративної автентифікації. Такі можливості можна додати після MVP.

### 1.4. Припущення та залежності

- Система обслуговує орієнтовно **до 200 працівників** однієї організації.
- Компанія має корпоративний Identity Provider (**IdP**) з підтримкою **OpenID Connect (OIDC)**, у якому керує користувачами й групами.
- Вміст файлів зберігається в приватному **S3-сумісному object storage**; він підтримує multipart upload і підписані URL.
- Максимальний розмір одного файла для MVP — **2 GiB**; частина multipart upload — орієнтовно **8 MiB**, кількість паралельних частин — **не більше чотирьох на клієнта**.
- Усі URL і домени `example.corp` у прикладах є **умовними**, а всі параметри доступності та продуктивності — **цільовими вимогами**, не результатами вимірювань готової системи.

### 1.5. Термінологія

| Термін | Значення |
|---|---|
| **Workspace** | Робочий простір команди або відділу з політиками й членством |
| **ACL** | Правила доступу користувачів до файлів та просторів |
| **SSO / IdP** | Єдиний корпоративний вхід / постачальник ідентичностей |
| **BFF** | Backend for Frontend: бекенд керує сесією вебклієнта |
| **Multipart upload** | Передавання файла частинами, які завантажуються незалежно |
| **Signed URL** | Короткоживуче посилання для конкретної операції зі сховищем |
| **CAS** | Compare-and-swap — атомарне оновлення за умови збігу версії |
| **Retention / legal hold** | Правила строку зберігання / заборона фізичного видалення |
| **MVP** | Мінімальна працездатна версія продукту |

## 10. Верифікація та критерії готовності

### 10.1. Матриця трасування вимог

| Вимоги | Сценарій перевірки | Артефакт / маршрут |
|---|---|---|
| FR-01–03 | SSO, список просторів, права на створення папки | `/me`, `/workspaces`, `/workspaces/{id}/folders` |
| FR-04–06 | Upload нового файла, повтор `complete`, AV/checksum, статус | C1, C4; `/uploads/*` |
| FR-05, FR-08 | Одночасні заміни і відновлення версій | C2; `/files/{id}/versions/*` |
| FR-07, FR-09 | ACL відмова, скачування до/після revoke | C3; `/download-link`, `/permissions/*` |
| FR-10 | Тимчасове посилання, чужий одержувач, revoke | `/share-links/*` |
| FR-11 | Пошук не показує чужі метадані | `/search` |
| FR-12, FR-15 | Кошик, legal hold, race recovery/purge | C5; `/recover`, `/legal-hold` |
| FR-13–14 | Audit + політики квот і retention | `/audit-events`, `/policy` |
| NFR-01–03 | Uptime- та навантажувальні випробування | Моніторинг, load-test report |
| NFR-04–05, NFR-10 | TLS, cookie flags, private bucket, TTL signed URL | Security/configuration tests |
| NFR-06–09 | Restore backup, structured logs, browser/keyboard tests | Операційні та UI test reports |

### 10.2. Мінімальні інтеграційні тести

1. Працівник `VIEWER` читає дозволені метадані, але отримує `403` на upload.
2. Двоє працівників завершують нову версію з однаковим `expectedVersionNo`: один `202`, другий `409`.
3. Спроба скачати новий файл до сканування повертає `409`; після позитивного сканування видається URL; після негативного — `422` або зберігається доступ лише до попередньої `CLEAN` версії.
4. Подвійний `complete` з однаковою `Idempotency-Key` не створює два записи версій.
5. Після відкликання прямого ACL за відсутності інших джерел доступу не можна отримати новий signed URL; попередній діє не довше 60 с.
6. Прострочений або відкликаний share-link не дає доступу; посилання іншого одержувача також відхиляється.
7. Відновлення і purge за одночасного запуску завершуються взаємовиключно; legal hold перешкоджає purge.
8. Два worker-и з простроченими leases не створюють дублікати аудиту та не позначають неперевірений файл `CLEAN`.
9. Перевищення квоти двома конкурентними завантаженнями не призводить до перевищення `quotaBytes` у committed state.
10. Rate limiter повертає `429` із `Retry-After`; помилка валідації повертає `400 application/problem+json`.

## 11. Що змінено відносно початкового нарису

Вихідним матеріалом слугує `fileflow_report.pdf` (20 сторінок): у ньому уже запропоновано SSO, папки, версії, S3, ACL, аудит, retention та п'ять concurrency-сценаріїв. Для завдання, орієнтованого на **одну компанію і помірну складність**, застосовано такі зміни:

| У вихідному нарисі | У цій версії | Чому |
|---|---|---|
| Cloud-native microservices, gateway, Kubernetes | SPA + один modular monolith + worker | Менше сервісів, мережевих відмов та інфраструктури |
| Event bus/outbox, окремі search/ACL/scan services | PostgreSQL jobs і модулі одного бекенду | Зберігаються потрібні concurrency-гарантії без Kafka та кількох БД |
| Desktop sync входить до MVP | Desktop sync відкладено | Потребує значно ширшої моделі офлайн-конфліктів |
| Share-links з паролем/зовнішніми доменами | Лише внутрішній адресний доступ через SSO | Простіше контролювати дані однієї компанії |
| SSO OIDC/SAML, складні ABAC/DLP-політики | OIDC BFF, RBAC + персональний ACL, без DLP | Достатньо для базової корпоративної моделі |
| Multi-AZ, жорсткі цілі масштабування | Один deployment, вимірні MVP-SLO | Узгодження операційних цілей з бюджетом MVP |
| API описаний концептуально | 29 формально описаних операцій OpenAPI | Закриває вимогу завдання про OpenAPI/Swagger та помилки |

**Проєктні ризики:** якщо компанія вимагає миттєвого анулювання вже відкритих завантажень, прямі signed GET URL не підходять — потрібен контрольований download proxy або інша схема доставлення байтів. Якщо обов'язкові регуляторні строки зберігання/персональні дані, значення retention потрібно погодити із юристами та фахівцями з безпеки перед production.
